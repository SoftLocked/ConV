# Testing simultaneous users and failure recovery

There are two different capacity questions. The shipped browser room supports
up to 50 users with a bounded WebRTC overlay, and full meshes for rooms of up
to eight. Two hundred browser users could use four rooms of 50 or 25 rooms of
eight. A 200-person room remains beyond the tested/admitted capacity. A
200-member full mesh would need 19,900 pairwise connections; the native UDP
harness does not create those WebRTC connections.

## Reproduce the all-writer engine stress suite

```sh
cargo build --release -p conv-native-peer --bin conv-bench
python3 scripts/stress-native.py
```

Default: **200 writers**, each requesting five single-scalar mutations per
second for ten seconds, followed by a 30-second settling deadline. All writers
start on phase-aligned timers, creating burst load. Three seeds run for each of:

- Healthy concurrent inserts.
- One percent seeded outbound frame loss plus a partition between two halves
  during editing. Both halves continue writing, then repair after reconnection.
- Concurrent inserts and deletes: every third local operation deletes a prior
  insertion, preserving tombstones and immutable history.

Each peer has its own real UDP socket. Peers are Tokio tasks in one process on
loopback. Frame discard happens in the application before sending; this is not
an OS network emulator, WAN latency, independent processes or a process crash.
Run the suite serially without competing browser recordings or compilation.

Every pass requires:

1. All configured writers actually generate mutations. A requested load that the
   host cannot sustain is a failed load test, even if the smaller actual load
   eventually converges. The default gate is at least 95% of the requested load.
2. Every replica has identical full document state and exact causal summaries.
3. Every replica retains the complete number of mutations generated by all
   writers, including bootstrap. Text equality alone is insufficient.
4. Fault counters prove that the requested loss/partition actually happened.
   Deletion cases must contain tombstones.
5. Processes finish within the deadline, and CPU/RSS measurements exist. An
   optional `--max-rss-mib` adds a final resource-budget gate.

Reports, command lines, logs, CPU/RSS sidecars and failures are retained under
`benchmarks/stress-results/TIMESTAMP/`. The runner returns a nonzero status if any
case fails. The offered-load fraction is separate from convergence: a rate
failure is not evidence of lost data, and convergence below the requested rate
is not evidence of supporting that requested rate.

For a small development check:

```sh
python3 scripts/stress-native.py --peers 12 --seconds 4 --settle-seconds 8 --seeds 0
```

For additional seeds, increasing edit rates or longer finite runs:

```sh
python3 scripts/stress-native.py --seeds 3,4,5
python3 scripts/stress-native.py --edits-per-second 10
python3 scripts/stress-native.py --seconds 30 --max-rss-mib 4096
```

`--max-rss-mib` checks peak usage after a process completes; it does not enforce a
live memory limit. Use an OS/container memory limit and a separate load generator
on a staging host before deliberately approaching exhaustion. Histories and
tombstones grow by design, so increasing duration and rate increases retained
state. A long soak needs an explicit document/history budget, capacity-error
checks, and memory monitoring; it is not an indefinite operation guarantee.

## Test the browser product separately

Native load exercises the shared Rust CRDT, membership, encoding and repair. It
does not exercise browser scheduling, CodeMirror, IndexedDB, ICE/TURN or signaling
capacity. A realistic staging browser farm should:

1. Ramp through 25 rooms of eight independent browser profiles, distributed
   across load-generator hosts. Keep staging and production separate, and record
   any deliberately changed join/rate limits. The present signaling join budget
   is 120/minute per transport IP, so a one-IP burst of 200 joins should be
   rate-limited; that is an expected control, not lost document edits.
2. Give every writer identifiable contributions. Verify the expected content,
   then export/compare canonical CRDT histories and causal receipts. Include
   overlapping replacements, Unicode, multiline paste and concurrent deletion.
3. Measure local input responsiveness, remote visibility, achieved operation
   rate, memory/CPU, persistence latency/errors, connection failures, data-channel
   buffering and repair backlog. Use one clock per measurement; do not subtract
   unsynchronized clocks on different devices.
4. Disconnect groups, lose packets, throttle bandwidth, background tabs, force
   TURN, stop signaling, restart browsers and change networks. Repeat crashes
   before and after the local-save acknowledgement: only acknowledged saves are
   promised durable. Check slow peers cannot cause unbounded queues or discard
   retained history.
5. Compare all surviving replicas after edits stop and connectivity returns.
   Test ninth-participant rejection and unavailable-room behavior too. Increase
   load until a declared latency, throughput or resource budget fails; publish
   the failure boundary along with passing results.

Current browser automation covers 12-session overlays and an optional
50-independent-context integration test, plus direct and forced local
TURN, offline recovery, a signaling outage, composition events, save failures,
independent offline tabs and backup restore. The five-view organic recording checks simultaneous sentence edits, deletion,
rewriting and typo correction. Its 50-session mode adds 45 real background
reviewers on a declared staggered schedule. Fifty isolated contexts consume most
of the current WSL host’s memory; this is functional integration rather than
latency qualification. The initial 200-writer native suite and a 50-browser
long-note burst have retained failures. A distributed 200-browser farm,
real-network shaping and a long soak are **not yet run**. Physical-device
checks remain in [manual-validation.md](manual-validation.md).

## Regression strategy

Use deterministic simulator seeds to reproduce algorithmic faults cheaply, real
UDP stress to find transport/load problems, and browser/device tests to validate
the product. Preserve every failure's commit, seed, workload, logs and resource
measurements. Reproduce a failure, fix its cause, and add a regression before
rerunning the affected checks. Test results establish the declared workload and
environment; no finite suite proves the system can never break.
